# Sprint 5 Messaging Design

## Purpose

Move an accepted order from `Pending` to `Processing` through a durable, observable, duplicate-safe asynchronous path. Sprint 5 adds the smallest production-shaped messaging slice; it does not add fan-out, production infrastructure, or private networking hardening.

## Decisions

- Use the transactional outbox pattern. The API commits the order, idempotency record, and `OrderCreatedIntegrationEventV1` outbox message in one SQL transaction.
- Use a timer-triggered publisher Function. One atomic SQL `UPDATE ... OUTPUT` claim, based on database UTC, leases at most 500 unpublished rows to a unique owner/token for 90 seconds before network I/O. The sender begins only with enough lease time for its bounded send deadline and conditional mark, renews its matching token if necessary, and marks a row published only when that token still matches. A stale-token mark affects zero rows, is recorded distinctly, and never causes an immediate re-send. Only expired leases are reclaimed. A crash after send can cause a duplicate send after reclaim, which is safe because the stable `EventId` reaches the duplicate-safe inbox; eventual publication must be proven against SQL Server.
- Use a Service Bus-triggered processor Function. A unique `InboxMessage.EventId` constraint makes the Inbox insert an atomic claim; it and `Pending` to `Processing` occur in the same SQL transaction. A unique-key collision is a successful duplicate no-op.
- Use one Azure Service Bus **Standard** namespace shared by non-production environments. It contains exactly two queues: `development-orders` and `test-orders`.
- Keep environment boundaries through queue names, separate Function Apps, separate storage/configuration, and environment-scoped managed identities. Neither runtime receives permission for the other environment's queue.

## Message Contract and Failure Handling

`OrderCreatedIntegrationEventV1` contains required `EventId` (UUID), `OrderId` (UUID), `OccurredAtUtc` (UTC ISO-8601), `messageType`, `messageVersion`, and W3C `traceparent` metadata. The body `EventId` must equal broker `MessageId`; the stored outbox JSON is reused unchanged for retries. `InboxMessage` retains handler, order ID, type/version, and canonical payload hash. An EventId collision is a successful duplicate only when each retained identity value matches; a conflicting collision rolls back and is dead-lettered with a sanitized stable reason. Application logs include message/order identifiers and delivery count, but never payload secrets.

Queues use a five-minute lock and `maxDeliveryCount` of five. The publisher has an eight-minute maximum drain; the processor uses PeekLock with `AutoCompleteMessages=false`, raw `ServiceBusReceivedMessage` plus `ServiceBusMessageActions`, no prefetch, batches of at most 20 (minimum five, five-second maximum wait), bounded parallelism starting at four, a five-minute host timeout, three-minute invocation limit, and 20-second per-message deadline. Host lock renewal exceeds the invocation limit; the application stops early enough to retain SQL and settlement margin. The publisher preserves pending rows if Service Bus is unavailable or a process ends after a send but before SQL acknowledgement. The processor claims inbox state transactionally, then completes the broker message only after SQL commit. On lock renewal/loss, execution timeout, or settlement failure it does not apply any further broker state; redelivery is made safe by the committed Inbox transaction. Transient broker or SQL failures abandon the message for retry. Invalid message type/version/payload are manually deserialized and dead-lettered immediately; Service Bus dead-letters a transient failure after its fifth delivery, always with a sanitized reason.

Functions emit structured lifecycle logs/traces and low-cardinality counters for pending-outbox count and oldest age, publish success/failure, delivery attempts, inbox duplicates, and processing success/failure. Order, event, and broker identifiers remain log/trace fields, never metric dimensions. Azure Monitor owns queue depth and DLQ metrics filtered by `EntityName`; an external scheduled query or canary detects telemetry silence. The Sprint 5 evidence includes runbook steps for investigating stalled outbox rows and replaying a sanitized DLQ message; alert ownership and production thresholds remain a later, explicitly approved operational decision.

## Boundaries

Sprint 5 provisions only the shared Standard namespace, environment queues, four minimum isolated Function identities (publisher and processor per environment), required storage, and least-privilege roles for development and test. Service Bus local/SAS authentication is disabled; Functions use managed-identity `fullyQualifiedNamespace` connections. Each publisher receives `Azure Service Bus Data Sender` only for its environment queue; each processor receives `Azure Service Bus Data Receiver` only for its environment queue, with no inherited namespace or resource-group data roles. A separate environment-scoped replay identity receives sender and receiver only for its environment queue: it sends a copied message preserving body, required properties, `EventId`, and `MessageId`, confirms the send, then completes the DLQ source. A failed completion is safe to rerun; Service Bus owns the new sequence/delivery state and the replay ID is recorded separately. Host storage uses managed identity; SQL uses contained users with the minimum application data permissions and no migration DDL permissions. Deployment verification must prove cross-environment send and receive attempts are denied after RBAC propagation. Azure Functions hosting hardening, private networking, full local-platform reproducibility, topics/subscriptions, and production deployment remain later sprint work.

## Verification and Promotion

Real SQL Server integration tests prove atomic claim/reclaim, stale-token rejection, eventual publication, Inbox uniqueness, and order/outbox transaction boundaries. Unit and fault-injection tests prove exact crash boundaries. The Service Bus emulator is limited to supported sequential broker flows; it is not proof of Entra RBAC, multi-instance concurrency, platform metrics, or real lock/settlement behavior. Local verification covers happy path, duplicate delivery, concurrent publisher drain, broker outage/recovery, crash-after-send, invalid payload, and poison/DLQ behavior. It must prove first request, exact idempotent replay, conflicting-payload rejection, concurrent same-key submission, and a failed transaction leave exactly one—or, on rollback, zero—order, idempotency, and outbox records. Azure development verification proves lease reclaim, lock loss before/after SQL commit, settlement failure, timeout, DLQ replay, queue-scoped RBAC denial, platform metrics, and `Pending → Processing`. After promotion, a QA-only test-environment pass exercises successful, boundary, invalid, authorization, failure/recovery, state-integrity, concurrency, and regression paths. No test → master promotion is part of this sprint.
